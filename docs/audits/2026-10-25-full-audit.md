# HKSCDA repository audit and P0 cleanup

Audit date: 25 October 2026, America/New_York. Repository: `YNWAforever/hkscda`. Baseline: `3c5574b5348273fc3a26c7ae6cc77e29cc6ae921` (`main`). Cleanup branch: `codex/full-audit-p0-cleanup-20261025`.

One P0 privacy defect was reproduced and fixed: application telemetry included private status-link bearer tokens. The cleanup changes three telemetry modules and adds eleven regression tests. Product journeys, permissions, database schema, dependencies and payment behavior are unchanged.

P0 means severe credential/data exposure or a core outage requiring immediate remediation. P1 means important authorization, correctness or verification risk. P2 means maintainability, resilience or latent hardening work. Priority describes remediation urgency, not proof of a production incident. Production token disclosure was **not** established.

## P0 implementation and regression evidence

- `src/lib/analytics.ts`: make the existing three status-path patterns case-insensitive; derive redacted current-page and referrer overrides for application-created GA configurations and custom events. Sensitive referrers lose their token, query and fragment. Ordinary event attributes and malformed-referrer handling are preserved.
- `src/lib/help/analytics.ts`: sanitize both the current and explicitly supplied Help `page_path`, preserving existing search-query sanitization and event semantics.
- `src/lib/lovable-error-reporting.ts`: sanitize the route context and prevent caller context from replacing it with a bearer path. Error messages/stacks remain unchanged; general error-payload and SDK enrichment policy belongs to AUD-06.
- `src/lib/telemetryPrivacy.test.ts`: eleven behavioral tests cover all three status families, case-insensitive routing, Help boundaries, GA configuration/events/referrers, error context, normal metadata and server-side safety. Before implementation, nine failed and two passed; afterward all eleven passed. The existing analytics/help/donation tests also passed: 39 tests across four files.
- Built-browser checks used synthetic invalid status tokens with the local read-only fixture. Opening the real Help widget emitted a redacted event on all three status pages, including mixed-case paths. No real applicant data or external analytics collector was used. These checks verify browser → widget → telemetry boundary, not real status lookup authorization or Google ingestion.

## Coverage and limits

The inventory covers 1,998 tracked `src/` files, 315 scripts, 255 Supabase files, 112 public assets, two native server handlers and 7,182 documentation files. There are 199 source API route declarations. Inventory/reference/signature scans and the full existing test command are broad automated coverage, not a claim that every source line or UI action was manually reviewed.

Deep tracing sampled these high-impact paths: admin bearer validation → live admin role/status lookup → role checks; supporter recovery → verified identity → records/receipt ownership → short-lived signing; donation admission/idempotency → provider checkout → signed webhook → settlement checks → receipt/delivery recovery; adoption/sponsorship upload intents and status tokens; volunteer/job authorization and cron configuration; public form body/rate/challenge boundaries; browser analytics and exception routing; migration RLS/search-path/grant guards and sensitive public projections.

Apparent anonymous view/table exposures were checked against later revocations and migration loops before being rejected. The portal binds verified Auth identity and submission email, and receipt access checks every included donation. These are repository findings, not a fresh production authorization assessment.

Tracked uncompressed files were scanned for common private-key, Stripe-live, AWS-access-key, GitHub-token and JWT signatures. No production credential was identified in those matches; all 112 JWT matches decoded to demo fixture issuers. A committed PEM is a public certificate. This does not cover Git history, compressed captures, images/OCR, every personal-data format or live logs. No secret values are reproduced here.

No safely removable dependency was established. Apparently unused direct dependencies may satisfy framework peer requirements or reusable UI modules; for example `date-fns` is used through `react-day-picker`. A dependency graph audit must distinguish unused declarations, reachable bundles and transitive requirements before deletion.

Public fixture brand coverage is 26 representative routes at five viewport sizes, not all admin/public actions. Real Auth, payments/email, deployed grants, provider configuration, production traffic/latency, automated-collector settings and authenticated admin browser workflows remain untested. Repository/live deployment version parity is unknown.
