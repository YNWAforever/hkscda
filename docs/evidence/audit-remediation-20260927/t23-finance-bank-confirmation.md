## Change and staff boundary

The canonical CSV dry-run from #172 remains the first step. Only one-to-one candidate_exact rows with matching payment reference and amount can be selected. The server reparses the original CSV and repeats candidate lookup before creating a 15-minute persisted snapshot. Duplicate bank references or payments within the selection are rejected. The selected rows are shown 25 per page; each pending row has its own confirmation button and a native confirmation dialog naming the bank reference, payment ID and amount. Recovery reads the operation by ID; completed, skipped and conflicted rows cannot be applied again. A per-item CSV shows result and reason.

The service-only SQL RPC repeats current confirmed, active, non-banned treasurer/admin checks under row locks. Apply locks the operation, item, payment and donation; checks the pending states, timestamp versions, HKD amount and normalized bank reference; then invokes the existing atomic manual-reconciliation RPC in the same transaction. The result records one payment/audit fact and one durable delivery job, with no immediate email/provider call. A changed row is a conflict, and the operator must make a new snapshot. This path never refunds, approves adoption, merges identities, sends reminders or performs unattended bulk settlement.

## Migration and rollback

One additive migration creates two RLS-enabled service-read tables and three service-only public RPCs, with a private current-actor guard. No old webhook, reconciliation, payment or receipt facts are removed. Before any production rollout, compare current catalog/signatures/grants/RLS/indexes and normalized historical references; rehearse on a sanitized data-bearing clone with lock timing and backup/restore. Do not blindly db push or fill migration ledger entries.

If a fault occurs, disable new bank-match UI/API and new checkout/admission as needed while preserving existing webhook intake, reconciliation and durable delivery jobs. Do not revert a succeeded payment to pending because receipt/email delivery failed. Keep additive schema and committed facts until a compatible older app SHA has been measured. No main merge, public preview, production DDL, payment enablement, content publication, real email or refund was performed.

## Payment-hint race correction

A red isolated DB assertion reproduced a real preview-to-snapshot gap: a selected payment with a mismatched current provider reference was incorrectly stored as pending by the first #175 SQL. The final migration persists the canonical CSV payment hint, checks it against the locked current payment when creating each snapshot item, and repeats that check when applying an item. A changed hint is skipped at preview or becomes a per-item conflict at apply; the test forces an apply-time hint change without a timestamp bump to prove this independent fence. Staff review and its confirmation dialog show the hint. The final exact SQL hash and 6332x data-bearing upgrade above supersede the earlier provisional #175 checksum and 6232x continuation rehearsal.
