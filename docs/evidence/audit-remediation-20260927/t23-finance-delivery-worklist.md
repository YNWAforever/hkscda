## Reproduction and change

- A rollback-only synthetic DB test showed the old `retry_donation_delivery_job_with_audit(uuid,uuid)` accepted an Auth-banned treasurer while `admin_user` remained active. The replacement checks current active treasurer/admin, Auth confirmation and ban under share locks, then locks the job and its successful payment/donation facts. Only `retryable` or `attention_required` may become `pending`; the update and one audit insert share a transaction. Replay, completed, processing, pending or refunded facts return false without another audit.
- A second red DB test found no DB-guarded private listing, and a red repository test caught direct table reads through the service client. The new service-role-only `list_failed_donation_delivery_jobs(uuid,integer)` rechecks the same current actor, bounds pages to 25 rows and 1–1,000 pages, and returns only failed job/payment status fields with no donor contact. The API passes its verified actor to this RPC. A direct request from a non-finance role or a subsequently banned actor is denied. Unknown source errors return unavailable, not a zero count.
- A red task-card test showed `retryable` jobs were omitted. It now counts both failed states and links to `#delivery-jobs`. The finance screen displays job/payment IDs, status, attempts and error code. A retry button appears only while payment and donation both say succeeded; each retry requires a staff confirmation, uses the existing audited route, then refreshes the list and task metric. There is no bulk retry, settlement, void or refund path. A stale browser cannot override the SQL guard.
