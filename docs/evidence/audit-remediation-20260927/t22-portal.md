# T22 / CRM-01 verified portal slice

Status: implementation under review, stacked after recovery PR #156. This slice provides fresh bearer verification through Supabase Auth on every records, receipt and preference request. The server derives the email from the verified principal and accepts no caller-selected supporter ID. No-store applies to sensitive responses. The client aborts stale requests, keys loaded data by token and clears the React Query cache on sign-out.

The records view shows only bounded, same-email adoption/donation snapshots and sponsorship submissions with a matching immutable submitted email. Legacy sponsorship rows without a submitted contact snapshot, ambiguous historical identities, and original status links whose raw token was retained only as a hash require staff assistance. The portal does not manufacture a status link or merge identities. Issued receipts are visible/downloadable only if every linked donation remains owned by the same supporter and matching contact email; a 60-second URL is signed for the private receipt bucket. The portal offers explicit marketing email opt-in/opt-out, separate from transactional receipts and case notices. The preference RPC commits consent and audit atomically. It does not automatically subscribe a user on login.

Evidence: ownership and UI tests first failed then passed; isolated SQL checks passed for opt-in, duplicate, opt-out, wrong email, unconfirmed user and banned user. Full isolated suite passed 2844/89 skipped, with typecheck, lint and build exit 0. CI, browser with actual OTP test sink and hosted OTP settings remain to be recorded. The loopback DB currently has the function manually applied without a new ledger row. No production migration, real email, deployment or marketing activation occurred.

Staff handling: When no record is safely linked or a status token has expired, ask the person for their original status link/reference through the existing verified staff process. Do not send a raw receipt URL or link two supporter identities solely because names match. Existing transaction notices follow their own service policy; a portal marketing opt-out does not void a payment or suppress a required case/receipt notice.
