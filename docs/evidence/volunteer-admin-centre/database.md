# Volunteer admin directory database evidence

Date: 2026-09-14 (Asia/Hong_Kong)
Branch: `feat/volunteer-admin-operations-centre`

## Change and scope

The additive migration is `supabase/migrations/20260913180745_volunteer_admin_directory_read.sql`. Its filename was created by `bunx supabase migration new volunteer_admin_directory_read`, after inspecting command help. It creates only `public.volunteer_admin_directory_read(uuid,jsonb)` and its execute permissions. It does not alter tables, rewrite records, backfill identities, or change policy/attendance history.

The current `volunteer_profile.auth_user_id` column is `NOT NULL`, unique, and references `auth.users`. This existing invariant was confirmed in the dedicated local database and retained. A truly unlinked profile fixture cannot exist under this schema. The left join and nullable email projection are defensive; they do not introduce unlinked profiles or infer account matches. Existing legacy registrations without canonical profile links remain in the existing reconciliation workflow and are not silently counted as profile-owned history.

## Restricted projection

The HTTP handler authenticates the request with `requireAdmin(request, ["staff", "admin"], client)` before reading. The SQL function independently requires an active staff/admin row, a confirmed actor email, and no current auth ban. It is `SECURITY DEFINER` with pinned `search_path=public,pg_temp`, because the server needs a narrow join against `auth.users`. Execute is revoked from PUBLIC, anon and authenticated, and granted only to service_role. No auth token, password, auth metadata, or service key is returned.

The directory explicitly selects profile fields plus only linked email, email verification and account-link status. It validates `q` (maximum 200 characters), status, tier, page (1–1,000,000), and limit (1–50). Defaults are page 1 and limit 25. `strpos(lower(...), lower(query))` makes `%` and `_` literal characters rather than wildcard syntax. Ordering is `lower(display_name), id`; total and page are computed in one SQL statement.

A selected canonical profile returns explicit credentials, registration/activity fields, append-only attendance facts and verification-event metadata. Each detail array is capped at 100, with uncapped totals in coverage metadata. Coverage explicitly says `linked_profile_records_only` and preserves nullable `history_coverage_start`. It does not infer service seniority or claim complete historical coverage. Missing profiles return HTTP 404. HTTP responses generated by the directory handler use `Cache-Control: no-store`; safe errors do not disclose database messages.

## Local installation and migration limits

All database activity for this slice targeted only `127.0.0.1:56322/postgres`, the dedicated isolated volunteer test database. Shared port 55322 and production were not used.

The function was initially absent. The database test was run and failed with PostgreSQL 42883 (`volunteer_admin_directory_read(uuid,jsonb) does not exist`). This installed the function for iterative verification without changing `supabase_migrations.schema_migrations` or any other migration ledger.

No full migration replay, `db reset`, production migration, or production query was performed. Local direct installation is not evidence that every historical migration replays successfully. The committed migration file remains the release artifact for a separately approved deployment.

## Rollback and compatibility

Rollback SQL for the new read function is:

```sql
DROP FUNCTION public.volunteer_admin_directory_read(uuid, jsonb);
```

Use this only with the application reverted to a version that no longer calls the new directory/detail API, or while that feature is deliberately disabled. Dropping the function while the new UI is active causes directory requests to fail. Do not use CASCADE, delete canonical records, replay old migrations, or change the auth-link invariant to roll this feature back. A deployed environment with a recorded migration should use its normal approved forward rollback process rather than manually deleting migration-ledger entries.

Locally, the DROP was tested inside a transaction: the function became absent, the canonical profile count remained unchanged, and the transaction was deliberately rolled back. A subsequent check confirmed the function was restored and the profile count still matched. This proves the function's local removal does not mutate profiles; it is not production rollback execution evidence.

## Legacy qualification-list regression repair

A browser check of the existing legacy qualification read exposed HTTP 500. The isolated SQL regression reproduced PostgreSQL **42702**, `column reference "a.id" is ambiguous`, at the `list_legacy` RETURN expression in `volunteer_legacy_identity_command`. Both SQL aliases `r`/`a` duplicated PL/pgSQL record-variable names declared by the function. The existing link-focused test did not exercise this read branch.

A separate forward migration, `supabase/migrations/20260913182552_volunteer_legacy_list_alias_fix.sql`, was created with `bunx supabase migration new volunteer_legacy_list_alias_fix`. Earlier applied migrations were not edited. The new migration reads the existing function definition, requires exactly one match for the expected list expression, and replaces only its SQL aliases with `legacy_registration` and `legacy_activity`. An unexpected prior function shape fails closed for review. The generated CREATE OR REPLACE retains the function's existing authorization, mutation body, security settings and execute ACL; no grants or table data are changed.

The migration was executed directly only on the dedicated local database at port 56322, without changing migration-ledger rows. Before/after catalog and definition checks confirmed:

- Identical execute ACL.
- Identical SECURITY DEFINER flag and pinned search path.
- Byte-identical function body from the `link_legacy` branch onward.

`src/lib/volunteers/directory/legacyList.database.test.ts` first failed with 42702, then passed after the migration: **1 test, 9 assertions**. It checks readable eligible legacy rows and their original identity fields; explicit linking and repeated idempotent linking; removal from the unlinked list after linking; preservation of submitted contact name; one durable link record; original execute grants; and ordinary-user rejection. All synthetic records are transactionally rolled back.

Reproduce the regression check using the dedicated test environment variables documented above:

```powershell
bun test src/lib/volunteers/directory/legacyList.database.test.ts
```

The combined directory and migration/audit checks after this repair passed **49 tests, 620 assertions**. This comprises directory checks **6/47** and existing guards **43/573**. Focused ESLint also passed. The browser verification owner was notified to retry the local qualification page; its browser result belongs to the separate browser evidence.

This repair changes no public function signature and is compatible with the prior application caller. An application rollback can retain the corrected database function. Reintroducing the ambiguous aliases would deliberately restore the read failure and is not a useful rollback. Any future database change should be a reviewed forward migration; do not replay the historical migration or delete ledger entries. No production application or production rollback occurred.
